# 관리 PIN 및 Emergency Pass 정책·구현안

- 문서 상태: 구현 반영 기준서
- 작성 기준일: 2026-09-01
- 대상 앱: ScreenRest(폰 쉼)
- 목적: PIN의 역할과 고행 3단계 Emergency Pass의 권한을 분리하고, 기존 구현을 안전하게 단순화한다.

> 구현 상태: 단일 관리 PIN, 안전 복구, Emergency Pass 영향 확인·현재 앱 한정·정책 종료 시점·사용 후 7일 제한을 코드에 반영했다. 기존 Emergency Pass 사용 기록은 유지하고 레거시 긴급 PIN만 마이그레이션에서 폐기한다. 컴파일과 실기기 시나리오 검증은 별도로 수행한다.

## 1. 최종 결론

ScreenRest의 인증 수단은 **관리 PIN 하나로 통합**한다.

Emergency Pass는 별도의 PIN이나 비밀번호가 아니다. 고행 3단계에서만 사용할 수 있고, 사용 후 7일 동안 다시 사용할 수 없는 **횟수 제한형 예외 권한**이다.

두 개념은 다음과 같이 구분한다.

| 구분 | 역할 |
|---|---|
| 관리 PIN | 이 작업을 실행하는 사람이 관리자임을 확인하는 인증 수단 |
| Emergency Pass | 고행 3단계에서도 특정 앱에 한 번 예외를 허용할 수 있는 제한된 권한 |

관리 PIN을 알고 있다는 사실만으로 고행 3단계를 일반 해제할 수는 없다. 관리 PIN으로 본인 확인을 한 뒤, 아직 사용 가능한 Emergency Pass가 있을 때만 예외를 만들 수 있다.

즉 다음 식으로 이해하면 된다.

> 관리 PIN = 사람을 확인한다.  
> Emergency Pass = 할 수 있는 행동의 범위와 횟수를 제한한다.

## 2. 변경 전 구현 상태

현재 앱에는 다음 세 요소가 혼재되어 있다.

### 2.1 관리 PIN

현재 관리 PIN은 다음 작업에 사용된다.

- 정책 저장 및 변경
- 기기 역할 변경
- 부모·자녀 연결 코드 생성과 등록
- 연결 해제
- 시간 추가 및 오늘만 허용
- 고행 1·2단계 종료 확인
- 계정 및 클라우드 데이터 삭제
- 안전 기능 일부 확인

### 2.2 긴급 PIN

현재 긴급 PIN은 관리 PIN과 별도로 최초 설정하도록 되어 있다.

- 인터넷 없이 Safe Mode로 복구하는 긴급 해제
- 고행 3단계 Emergency Pass 사용
- 설정 탭에서 별도로 변경

### 2.3 Emergency Pass

현재 Emergency Pass의 핵심 상태는 이미 다음과 같이 구현되어 있다.

- 고행 3단계가 실제로 차단 중일 때만 사용 가능
- 현재 차단된 앱에 정책별 예외 부여
- 스케줄은 현재 스케줄 종료까지 유지
- 허용앱만·요일별·앱 그룹·앱별 제한은 원칙적으로 자정까지 유지
- 사용한 정확한 시각부터 7일 후 다시 사용 가능
- 모든 앱과 모든 고행 3단계가 하나의 재사용 대기시간을 공유
- 사용하지 않은 Pass가 여러 장으로 누적되지 않음

현재 핵심 문제는 Emergency Pass 자체보다 **긴급 PIN과 관리 PIN의 역할이 사용자에게 중복되어 보인다는 것**이다.

## 3. 현재 구조의 문제점

### 3.1 사용자에게 두 PIN의 차이가 직관적이지 않다

관리 PIN과 긴급 PIN 모두 결과적으로 차단 또는 정책 상태를 변경하는 화면에 나타난다. 사용자는 어떤 PIN을 언제 입력해야 하는지 외워야 한다.

### 3.2 긴급 PIN이 두 가지 의미를 동시에 가진다

긴급 PIN은 현재 다음 두 작업에 함께 사용된다.

1. 앱 오작동 시 안전 복구
2. 고행 3단계에서 Emergency Pass 소비

안전 복구와 사용 제한 예외는 성격이 다르므로 같은 이름으로 묶으면 혼란이 생긴다.

### 3.3 별도 PIN이 고행 3단계의 강도를 높여주지는 않는다

두 PIN을 모두 같은 부모나 동일 사용자가 관리한다면, 비밀번호를 하나 더 만드는 것이 실질적인 권한 분리로 이어지지 않는다. 오히려 분실·오입력·지원 문의 가능성만 높인다.

### 3.4 Emergency Pass의 실제 영향 범위가 화면에 충분히 설명되지 않는다

현재 화면에는 `Emergency Pass 사용`과 7일 주기 정도만 보인다. 하지만 실제 사용자는 다음을 사용 전에 알아야 한다.

- 어느 앱이 허용되는가
- 언제까지 허용되는가
- 어떤 차단 정책에 예외가 생기는가
- 다음 사용 가능 시각은 언제인가
- 사용 후 취소하거나 되돌릴 수 있는가

### 3.5 블록 화면 구현 경로가 두 군데다

현재 블록 UI와 동작이 `BlockedActivity`와 `UsageMonitorForegroundService` 양쪽에 존재한다. 한쪽만 수정하면 기기나 실행 경로에 따라 예전 PIN 또는 예전 문구가 다시 나타날 수 있다. 두 경로를 반드시 같이 수정해야 한다.

## 4. 관리 PIN 최종 정의

### 4.1 형태

- 숫자 4~8자리
- 최초 설정 시 두 번 입력
- 평문 저장 금지
- 기존 PBKDF2-HMAC-SHA256 해시 저장 구조 유지
- 5회 연속 실패 시 30초 잠금 유지
- PIN 입력값은 화면 이동, 앱 백그라운드 전환, 성공 또는 취소 시 즉시 비움

### 4.2 관리 PIN이 필요한 작업

#### 정책 및 계정 관리

- 5가지 차단 정책 저장
- 고행 단계 적용 및 허용된 범위 내 단계 변경
- 기기 역할 변경
- 부모·자녀 연결 코드 생성·등록·연결 해제
- 제한 없는 앱 변경
- 계정 삭제

#### 일반 차단 해제

- 시간 추가
- 오늘만 허용
- 임시 허용 취소·정정
- 고행 1단계의 숙고 완료 후 정책 종료
- 고행 2단계의 30분 숙고 완료 후 정책 종료

#### 안전 복구

- 고행 3단계가 실제 활성 상태가 아닐 때 Safe Mode 복구
- 정책 감시 기능의 안전한 중단

#### Emergency Pass

- 고행 3단계 블록 화면에서 Pass 소비 전 관리자 확인

### 4.3 관리 PIN만으로 할 수 없는 작업

- 활성 고행 3단계를 즉시 끄기
- 활성 고행 3단계를 1·2단계 또는 사용 안 함으로 낮추기
- 고행 3단계에서 일반 시간 추가 또는 오늘만 허용 사용
- 부모 승인으로 고행 3단계 우회
- Emergency Pass의 7일 재사용 대기시간 초기화
- 이미 소비한 Emergency Pass의 취소 또는 환불

이 제한이 중요하다. 관리 PIN은 인증 수단이지 고행 3단계의 무제한 마스터키가 아니다.

## 5. Emergency Pass 최종 정의

### 5.1 기본 성격

Emergency Pass는 다음 조건을 모두 만족할 때만 사용할 수 있다.

1. 현재 앱이 실제로 차단되어 있다.
2. 차단 원인 중 하나 이상이 활성 고행 3단계다.
3. 마지막 사용 시각으로부터 7일이 지났거나 사용 기록이 없다.
4. 관리 PIN 인증에 성공했다.
5. 사용자가 영향 범위를 확인하고 최종 사용을 선택했다.

### 5.2 적용 범위

- Pass를 실행한 **현재 앱 하나**에만 적용한다.
- 현재 앱을 실제로 막고 있는 정책 키에만 예외를 만든다.
- 최소 한 개의 고행 3단계 정책이 포함되어야 한다.
- 동일 앱을 동시에 막고 있는 하위 단계 정책도 함께 우회해야 앱이 실제로 열리므로, 필요한 차단 원인만 함께 포함한다.
- 현재 앱과 관계없는 정책, 다른 앱의 정책에는 예외를 만들지 않는다.
- Pass 사용 후 새로 시작되는 미래 스케줄이나 새 정책에는 자동 적용하지 않는다.

### 5.3 허용 종료 시점

각 정책 예외는 해당 정책의 자연스러운 종료 시점까지만 유지한다.

| 차단 정책 | Emergency Pass 예외 종료 시점 |
|---|---|
| 요일별 제한 | 다음 로컬 자정 |
| 앱 그룹 제한 | 다음 로컬 자정 |
| 앱별 제한 | 다음 로컬 자정 |
| 허용앱만 모드 | 현재 고행 종료 시각, 없으면 다음 로컬 자정 |
| 스케줄 차단 | 현재 실행 중인 스케줄 구간의 종료 시각 |

스케줄이 자정을 넘어가는 경우 날짜가 바뀌어도 현재 스케줄 종료까지 유지한다.

### 5.4 재사용 주기

- 기준은 `마지막 사용 시각 + 7 × 24시간`이다.
- 특정 요일이나 자정 기준의 주간 초기화가 아니다.
- 사용하지 않아도 Pass가 두 장 이상 쌓이지 않는다.
- 모든 고행 3단계와 앱이 하나의 대기시간을 공유한다.
- 자녀 기기가 여러 대라면 기존 구조를 유지하여 **각 자녀 기기별로 별도 관리**한다.
- 앱 재설치나 데이터 삭제를 재사용 대기시간 우회 수단으로 악용하지 못하게 하는 클라우드 동기화는 별도 출시 후 보강 항목으로 둔다.

### 5.5 소비 규칙

다음 경우에는 Pass를 소비하지 않는다.

- 관리 PIN 오류
- 이미 7일 대기시간이 적용 중임
- 실제 고행 3단계 차단이 아님
- 대상 패키지 또는 차단 정책 정보가 비어 있음
- 저장 작업 실패
- 확인 팝업에서 취소

다음 시점에만 Pass를 소비한다.

> 관리 PIN 검증, 고행 3단계 재확인, 대기시간 재확인, 예외 저장이 하나의 원자적 저장 작업 안에서 모두 성공한 시점

소비 후에는 취소·환불하지 않는다. 앱을 바로 닫더라도 7일 대기시간은 유지한다.

### 5.6 고행 1·2단계와의 차이

| 단계 | 숙고 | 결과 | PIN | 반복 가능성 |
|---|---:|---|---|---|
| 1단계 숙고 | 2분 | 현재 앱 5분 임시 허용 | 임시 허용 자체에는 불필요 | 하루 최대 2회 |
| 2단계 통제 | 30분 | 해당 정책을 현재 적용 기간 동안 종료 | 관리 PIN | 정책별 |
| 3단계 절대 집중 | 일반 종료 없음 | 자연 종료까지 유지 | 관리 PIN으로도 일반 해제 불가 | 해당 없음 |
| Emergency Pass | 별도 숙고 없음 | 현재 앱을 현재 정책의 자연 종료까지 예외 허용 | 관리 PIN + Pass 1회 소비 | 사용 후 7일 |

Emergency Pass를 5분 또는 15분짜리 허용권으로 바꾸면 1단계와 기능이 겹치므로 그렇게 변경하지 않는다.

## 6. 안전 복구 기능 재정의

기존 `긴급 해제`라는 이름은 Emergency Pass와 혼동되므로 **안전 복구**로 변경한다.

### 6.1 안전 복구의 목적

- 앱의 감시 기능 오작동
- 정상 앱이 반복 차단되는 오류
- 권한 상태 불일치
- 블록 화면 반복 표시

정책을 편의상 우회하는 기능이 아니라 앱을 정상 상태로 되돌리는 진단·복구 기능이다.

### 6.2 인증

- 별도 긴급 PIN을 사용하지 않는다.
- 관리 PIN을 사용한다.
- 고행 3단계가 활성 상태라면 기존 원칙대로 일반 안전 복구로 정책을 끌 수 없다.
- 고행 3단계에서 특정 앱 사용이 반드시 필요하면 블록 화면의 Emergency Pass를 사용한다.

### 6.3 UI 명칭

| 기존 | 변경 |
|---|---|
| 긴급 PIN | 삭제 |
| 긴급 해제 | 안전 복구 |
| Emergency PIN | 삭제 |
| Emergency Unlock | Safe Recovery |

## 7. 사용자 화면 흐름

### 7.1 최초 설정

1. `관리 PIN 만들기`
2. 관리 PIN 입력
3. 관리 PIN 확인 입력
4. 역할 안내 확인
5. 저장

필수 설명:

> 관리 PIN은 설정 변경, 부모 연결, 차단 해제 확인에 사용됩니다. 고행 3단계는 관리 PIN만으로 즉시 종료할 수 없습니다.

긴급 PIN 입력 필드와 서로 다르게 설정하라는 검증은 제거한다.

### 7.2 일반 설정 저장

1. 설정 변경
2. 하단 `변경 있음 · 저장해야 적용됩니다` 표시
3. `저장` 선택
4. 관리 PIN 팝업
5. 성공 후 입력값 제거 및 `완료` 표시

### 7.3 고행 1단계

- 임시 사용: 2분 카운트다운 후 5분 사용, PIN 없음
- 고행 종료 또는 단계 하향: 2분 숙고 완료 후 관리 PIN
- 하루 최대 2회 제한과 남은 횟수 표시

### 7.4 고행 2단계

- 30분 숙고 시작
- 앱을 벗어나도 종료 시각을 저장하고 다시 돌아오면 남은 시간 표시
- 숙고 완료 후 관리 PIN
- 요일별·앱 그룹·앱별·허용앱만이면 `오늘 이 정책 종료`
- 스케줄이면 `이번 스케줄에서 종료`

### 7.5 고행 3단계에서 Emergency Pass 사용

#### 1단계: 버튼 상태

사용 가능:

> Emergency Pass 사용 가능 1회

대기 중:

> 사용 완료 · 다음 사용 가능 9월 7일 오후 3:00

#### 2단계: 영향 범위 확인

예시:

> YouTube를 오늘 자정까지 허용합니다.  
> 현재 적용 중인 고행 3단계와 함께 이 앱을 막고 있는 정책에만 예외가 적용됩니다.  
> 사용 후 7일 동안 다른 앱과 다른 고행 3단계에서도 Emergency Pass를 사용할 수 없습니다.  
> 사용 후에는 취소하거나 되돌릴 수 없습니다.

스케줄이면 종료 시각을 정확히 표시한다.

> YouTube를 오늘 오후 10:00, `공부 시간` 스케줄 종료까지 허용합니다.

버튼:

- `취소`
- `관리 PIN 입력`

#### 3단계: 관리 PIN 확인

- 제목: `Emergency Pass 확인`
- 필드: `관리 PIN`
- 버튼: `취소` / `Pass 사용`

#### 4단계: 결과

성공:

> YouTube에 Emergency Pass를 사용했습니다.

### 8.1 유지할 데이터

### 8.3 권장 인증 API

PIN 검증을 호출부마다 직접 선택하지 않도록 목적을 명시한다.

```kotlin
enum class AdminPinPurpose {
    PolicySave,
    Pairing,
    TemporaryOverride,
    HardshipLevel1Exit,
    HardshipLevel2Exit,
    EmergencyPass,
    SafeRecovery,
    AccountDeletion,
}
```

```kotlin
sealed interface AdminPinVerificationResult {
    data object Valid : AdminPinVerificationResult
    data object Invalid : AdminPinVerificationResult
    data class Locked(val untilMillis: Long) : AdminPinVerificationResult
}
```

이벤트 로그에는 PIN 값이 아니라 목적과 성공 여부만 남긴다.

### 8.4 권장 Emergency Pass 상태

```kotlin
sealed interface EmergencyPassAvailability {
    data object Available : EmergencyPassAvailability
    data class Cooldown(val nextAvailableAtMillis: Long) : EmergencyPassAvailability
    data object NoActiveLevel3Block : EmergencyPassAvailability
}
```

### 8.5 권장 사용 함수

```kotlin
suspend fun useHardshipEmergencyPass(
    adminPin: String,
    packageName: String,
```

저장소 내부 검증 순서는 다음과 같이 한다.

1. 대상 패키지 확인
2. 현재 앱을 막는 정책 키 재계산 또는 검증
3. 고행 3단계 정책 존재 확인
4. 7일 대기시간 확인
5. 관리 PIN 검증
6. 정책별 만료 시각 계산
7. 예외 목록과 마지막 사용 시각을 동일한 DataStore 편집에서 저장
8. 이벤트 로그 기록

버튼 표시 단계의 사전 확인만 믿지 말고 저장 직전에 모든 조건을 다시 확인해야 한다.

## 10. 기존 사용자 마이그레이션

### 10.1 원칙

- 기존 관리 PIN을 그대로 유지한다.
- 긴급 PIN을 관리 PIN으로 자동 승격하지 않는다.
- 기존 사용자는 새 PIN을 다시 만들 필요가 없다.
- Emergency Pass 마지막 사용 시각과 활성 예외를 그대로 유지한다.
- 업데이트로 7일 대기시간이 초기화되면 안 된다.

### 10.2 권장 순서

1. PIN 스키마 버전 추가
2. 관리 PIN 자격 증명 존재 여부 확인
3. 관리 PIN이 있으면 단일 PIN 설정 완료로 처리
4. 긴급 PIN 자격 증명은 더 이상 읽거나 검증하지 않음
5. UI에서 긴급 PIN 입력·변경 제거
6. 한 안정화 버전 후 긴급 PIN 해시와 실패 상태 삭제
7. 이벤트 로그에 `Emergency PIN retired; Admin PIN preserved` 기록

### 10.3 예외

관리 PIN이 없고 긴급 PIN만 존재하는 비정상 데이터라면 긴급 PIN을 자동 관리 PIN으로 바꾸지 않는다. 최초 관리 PIN 설정 화면으로 이동시킨다.

## 13. 완료 조건

다음 조건을 모두 만족해야 구현 완료로 판단한다.

- 앱 전체에서 사용자가 설정·기억해야 하는 PIN은 관리 PIN 하나뿐이다.
- 긴급 PIN 입력·변경·초기 설정 UI가 남아 있지 않다.
- 고행 3단계는 관리 PIN만으로 일반 해제되지 않는다.
- Emergency Pass는 관리 PIN 인증과 7일 권한을 모두 요구한다.
- Pass는 현재 앱과 실제 차단 정책에만 적용된다.
- Pass 사용 전 앱, 종료 시각, 다음 사용 가능 시각을 확인할 수 있다.
- 잘못된 PIN이나 저장 실패로 Pass가 소비되지 않는다.
- 사용한 Pass는 취소·환불되지 않는다.
- `BlockedActivity`와 서비스 오버레이의 버튼, 문구, 결과가 동일하다.
- 기존 사용자의 관리 PIN 및 Pass 대기시간이 유지된다.
- 고행 1·2단계, 부모 연결, 정책 저장 등 기존 정상 기능이 후퇴하지 않는다.

## 14. 최종 권장안

현재 Emergency Pass의 `현재 앱 한정`, `정책 자연 종료까지`, `전체 3단계 공통 7일 1회` 구조는 유지하는 것이 좋다. 이는 1단계의 짧은 임시 허용 및 2단계의 숙고 후 정책 종료와 구분된다.

수정의 핵심은 Emergency Pass를 약하게 바꾸는 것이 아니다.

1. 관리 PIN과 긴급 PIN을 관리 PIN 하나로 통합한다.
2. Emergency Pass를 별도 비밀번호가 아닌 제한된 권한으로 명확히 표현한다.
3. 사용 전에 앱·영향 정책·종료 시각·7일 제한을 보여준다.
4. 블록 화면의 두 구현 경로를 동시에 변경한다.
5. 기존 Pass 사용 시각과 고행 정책을 그대로 보존한다.

이 구조가 보안 강도와 고행 정책의 의미를 유지하면서 사용자 이해도를 가장 크게 높이는 방향이다.
